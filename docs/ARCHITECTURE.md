## 🎯 Общая философия

### Цель проекта
**"Гладкая разработка без танцев с бубном"** — наша главная цель. Мы строим предсказуемую, надежную систему, где каждый разработчик может быстро понять архитектуру и внести изменения без страха что-то сломать.

### Ключевые принципы

#### 1. **Single Source of Truth (Единый источник правды)**
- Все типы определены в одном месте: `apps/mdtclient/src/shared/types/index.ts`
- Схема базы данных — единственный источник истины для структуры данных
- Никаких дублирующихся определений типов в разных файлах

#### 2. **Нормализация данных**
- Четкое разделение гражданских и служебных данных
- Одна таблица — одна ответственность
- Связи через внешние ключи, а не через JSON-поля

#### 3. **Четкое разделение ответственности**
- Каждая схема БД имеет конкретное назначение
- Каждый слой фронтенда выполняет свою роль
- UI-компоненты изолированы и переиспользуемы

## 🗄️ Архитектура Базы Данных

### 2.1. Схемы Баз Данных

Наша база данных разделена на логические схемы, каждая со своей ответственностью:

#### **`auth`** — Аутентификация Supabase
- **Назначение**: Только для аутентификации и авторизации
- **Содержимое**: `auth.users`, `auth.identities`, `auth.sessions`
- **Доступ**: Управляется Supabase, не модифицируем напрямую

#### **`public`** — Публичные профили и VIEW
- **Назначение**: Публичные данные и обратная совместимость
- **Содержимое**: 
  - `public.profiles` — профили пользователей (связь с `auth.users`)
  - `public.legacy_users` — временная таблица для миграции
  - VIEW для обратной совместимости
- **Особенность**: Единственное место, где хранятся профили пользователей

#### **`common`** — Физические сущности игрового мира
- **Назначение**: "Реальные" объекты игрового мира
- **Содержимое**:
  - `common.characters` — гражданские данные персонажей
  - `common.leo_profiles` — служебные профили полиции
  - `common.ems_profiles` — служебные профили медиков
  - `common.vehicles` — транспортные средства
  - `common.companies` — компании и организации
  - `common.departments` — департаменты и подразделения

#### **`mdt`** — Операционные записи служб
- **Назначение**: Операционные данные MDT-системы
- **Содержимое**:
  - `mdt.reports` — отчеты и документы
  - `mdt.calls_911` — экстренные вызовы
  - `mdt.bolos` — бюллетени о розыске
  - `mdt.incidents` — инциденты и происшествия
  - `mdt.active_units` — активные подразделения

#### **`forum`** — Форумная система
- **Назначение**: Все, что связано с форумом
- **Содержимое**: темы, посты, комментарии, категории

### 2.2. Ключевые сущности и их связи

#### Нормализованная структура персонажей:

```
auth.users (UUID) 
    ↓ (1:1)
public.profiles (UUID) 
    ↓ (1:N)
common.characters (UUID owner_id)
    ↓ (1:1)
common.leo_profiles (UUID character_id) | common.ems_profiles (UUID character_id)
```

#### Почему такая структура?

1. **`auth.users`** — стандартная таблица Supabase, содержит только данные аутентификации
2. **`public.profiles`** — расширяет `auth.users` публичными данными (аватар, роли, настройки)
3. **`common.characters`** — содержит только гражданские данные (имя, адрес, лицензии)
4. **`common.leo_profiles`** — содержит только служебные данные полиции (значок, звание, департамент)

**Преимущества:**
- Четкое разделение гражданских и служебных данных
- Возможность иметь несколько персонажей на один аккаунт
- Легкое добавление новых типов служебных профилей
- Простые запросы без сложных JOIN'ов

### 2.3. Правила безопасности (RLS)

#### Принципы RLS-политик:

1. **Максимальная простота** — политики должны быть понятными и предсказуемыми
2. **Прямая проверка** — используем `auth.uid()` напрямую, без сложных подзапросов
3. **Роли через профили** — проверяем роли в `public.profiles`, а не в сложных JOIN'ах

#### Примеры "хороших" политик:

```sql
-- ✅ Хорошо: Простая проверка владельца
CREATE POLICY "Users can view own characters" ON common.characters
    FOR SELECT USING (auth.uid() = owner_id);

-- ✅ Хорошо: Проверка роли через профиль
CREATE POLICY "LEO can view all characters" ON common.characters
    FOR SELECT USING (
        EXISTS (
            SELECT 1 FROM public.profiles 
            WHERE id = auth.uid() 
            AND 'leo' = ANY(roles)
        )
    );

-- ❌ Плохо: Сложная рекурсивная проверка
CREATE POLICY "Complex role check" ON common.characters
    FOR SELECT USING (
        EXISTS (
            SELECT 1 FROM users u1 
            JOIN users u2 ON u1.department_id = u2.department_id
            WHERE u1.auth_id = auth.uid() 
            AND u2.id = owner_id
        )
    );
```

## 🎨 Архитектура Фронтенда (mdtclient)

### 3.1. Единый источник правды для типов

#### Золотой файл типов: `apps/mdtclient/src/shared/types/index.ts`

Этот файл содержит канонические типы для всех ключевых сущностей системы. **Любой новый код обязан использовать типы из этого файла.**

#### Пример "золотого" типа:

```typescript
// ✅ Канонический тип Character
export interface Character {
  id: string;
  ownerId: string; // UUID из auth.users
  
  // Гражданские данные
  firstName: string;
  lastName: string;
  dateOfBirth: string;
  address?: string;
  phoneNumber?: string;
  licenses?: any; // jsonb
  
  // Служебные данные (опционально)
  isUnit?: boolean;
  badgeNumber?: string;
  departmentId?: number;
  
  // Метаданные
  createdAt: string;
  updatedAt: string;
}
```

#### Правила использования типов:

1. **Импортируйте из shared/types** — никогда не создавайте локальные типы
2. **Используйте канонические имена** — `Character`, а не `UserCharacter` или `Person`
3. **Следуйте конвенциям именования** — camelCase для полей, PascalCase для интерфейсов

### 3.2. Feature-Sliced Design (FSD)

Наш фронтенд организован по принципу FSD с четким разделением слоев:

#### **`shared/`** — Общие ресурсы
- `shared/types/` — типы (единственный источник правды)
- `shared/ui/` — переиспользуемые UI-компоненты
- `shared/lib/` — утилиты и хелперы
- `shared/api/` — API-клиенты

#### **`entities/`** — Бизнес-сущности
- `entities/citizen/` — граждане и персонажи
- `entities/vehicle/` — транспортные средства
- `entities/company/` — компании
- `entities/incident/` — инциденты

#### **`features/`** — Функциональные возможности
- `features/auth/` — аутентификация
- `features/citizen-management/` — управление гражданами
- `features/law-enforcement/` — правоохранительная деятельность
- `features/ems-system/` — медицинская служба

#### **`widgets/`** — Сложные составные компоненты
- `widgets/officer-dashboard/` — дашборд офицера
- `widgets/citizen-portal/` — портал гражданина
- `widgets/dispatch-portal/` — портал диспетчера

#### **`pages/`** — Страницы приложения
- `pages/admin/` — административные страницы
- `pages/citizen/` — страницы для граждан
- `pages/dispatch/` — страницы диспетчера

### 3.3. Разработка UI в Storybook

#### Storybook — наша основная среда для UI

**Принцип**: Все новые UI-компоненты должны иметь "истории" в Storybook. Это наш живой UI-кит и документация.

#### Структура историй:

```typescript
// ✅ Правильная структура истории
import type { Meta, StoryObj } from '@storybook/react';
import { Button } from './Button';

const meta: Meta<typeof Button> = {
  title: 'UI/Atoms/Button',
  component: Button,
  parameters: {
    layout: 'centered',
  },
  tags: ['autodocs'],
  argTypes: {
    variant: {
      control: { type: 'select' },
      options: ['primary', 'secondary', 'danger'],
    },
  },
};

export default meta;
type Story = StoryObj<typeof meta>;

export const Default: Story = {
  args: {
    children: 'Кнопка',
    variant: 'primary',
  },
};
```

#### Запуск Storybook:

```bash
cd apps/mdtclient
npm run storybook
```

Storybook доступен по адресу: http://localhost:6006

## 🔄 Процесс разработки

### Правильный цикл разработки новой фичи:

#### 1. **Начни с данных** 📊
```bash
# Определи/обнови типы в shared/types
vim apps/mdtclient/src/shared/types/index.ts
```

**Правило**: Сначала определи, какие данные нужны, потом думай о UI.

#### 2. **Обнови БД** 🗄️
```bash
# Создай миграцию если нужно
cd supabase/migrations
# Создай новый файл: 020_add_new_feature.sql
```

**Правило**: Схема БД определяет типы, а не наоборот.

#### 3. **Разработай UI** 🎨
```bash
# Создай компоненты и истории в Storybook
cd apps/mdtclient/src/shared/ui/atoms/NewComponent/
# Создай NewComponent.tsx и NewComponent.stories.tsx
```

**Правило**: Каждый компонент должен работать в изоляции.

#### 4. **Реализуй логику** ⚙️
```bash
# Напиши сервисы и API на бэкенде
cd server/services
# Создай NewFeatureService.ts
```

**Правило**: Бизнес-логика на бэкенде, UI-логика на фронтенде.

#### 5. **Интегрируй** 🔗
```bash
# Собери все вместе на странице приложения
cd apps/mdtclient/src/pages/new-feature/
# Создай NewFeaturePage.tsx
```

**Правило**: Интеграция — последний шаг, а не первый.

### Пример разработки фичи "Поиск граждан":

1. **Данные**: Добавляем `CharacterSearchParams` в `shared/types`
2. **БД**: Создаем индексы для поиска в `common.characters`
3. **UI**: Создаем `SearchInput` и `CharacterList` с историями
4. **Логика**: Пишем `CharacterSearchService` на бэкенде
5. **Интеграция**: Создаем страницу поиска граждан

## 🚧 Технический долг и план его погашения

### 5.1. Подавленные ошибки TypeScript

#### Проблема
В проекте используется **67 файлов** с `// @ts-nocheck` — это наш "список долгов". Код работает, но не типобезопасен в этих местах.

#### Файлы с подавленными ошибками:
- **Виджеты**: 12 файлов (OfficerDashboardWidget, CitizenPortalNew, etc.)
- **UI-компоненты**: 15 файлов (UnitListWidget, StatusWidget, etc.)
- **Функциональности**: 25 файлов (LawControlPanel, PersonSearch, etc.)
- **Сущности**: 15 файлов (CitizenCard, VehicleCard, etc.)

#### План погашения:

1. **Приоритет 1** (критично): Виджеты и основные UI-компоненты
2. **Приоритет 2** (важно): Функциональности и сущности
3. **Приоритет 3** (желательно): Остальные компоненты

#### Как работать с `// @ts-nocheck`:

```typescript
// ❌ Плохо: Оставлять навсегда
// @ts-nocheck - TODO: Remove after major refactoring is complete

// ✅ Хорошо: Планировать исправление
// @ts-nocheck - TODO: Fix types after implementing shared/types
// Проблемы:
// - Line 45: any type for user data
// - Line 67: missing interface for API response
```

**Правило**: При работе с файлом, содержащим `// @ts-nocheck`, постепенно убирайте подавление и исправляйте типы.

### 5.2. Миграция на UUID

#### Проблема
Мы починили таблицу `common.characters`, но другие таблицы все еще могут использовать `integer` ID для авторов.

#### Таблицы, требующие миграции:
- `applications.author_id` → `uuid`
- `reports.author_id` → `uuid`
- `support_tickets.author_id` → `uuid`
- `complaints.author_id` → `uuid`

#### План миграции:

1. **Создать миграцию** для изменения типа колонок
2. **Обновить типы** в `shared/types`
3. **Исправить API** для работы с UUID
4. **Обновить фронтенд** для использования UUID

### 5.3. Удаление legacy-кода

#### Проблема
В системе остались временные таблицы и VIEW для обратной совместимости.

#### Что нужно удалить:
- `public.legacy_users` — после завершения миграции данных
- VIEW для обратной совместимости — после обновления всего кода
- Старые RLS-политики — после тестирования новых

#### План очистки:

1. **Аудит использования** — найти все места, где используется legacy-код
2. **Постепенная миграция** — перевести код на новые таблицы
3. **Тестирование** — убедиться, что ничего не сломалось
4. **Удаление** — убрать legacy-код

### 5.4. Документация и тестирование

#### Проблема
Недостаточно документации и автоматических тестов.

#### План улучшения:

1. **Документация API** — создать OpenAPI спецификацию
2. **Тесты компонентов** — добавить Jest тесты для UI
3. **Интеграционные тесты** — тестировать полные сценарии
4. **E2E тесты** — автоматизировать тестирование пользовательских сценариев

## 📚 Заключение

Этот документ — наша "конституция". Он определяет, как мы строим систему, чтобы избежать хаоса и обеспечить предсказуемость разработки.
